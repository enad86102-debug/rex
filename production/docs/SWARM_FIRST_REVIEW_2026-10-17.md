## 3. قائمة العيوب والعوائق حسب الأولوية

1. **P0 BLOCK — لا لعبة عامة:** `service.go` يرد `rules_not_approved` على start، ولا API أفعال مباراة أو نتائج أو Tarneeb. لا يجوز تجاوز البوابة بلا عقد قواعد معتمد.
2. **P0 BLOCK — حفظ المباراة غير موجود:** [Match](../server/internal/games/trixcomplex/engine.go) يحتفظ بالأيدي والسجل في الذاكرة؛ لا معاملة تربط فعلًا وإيصالًا وحدثًا وحالة ونتيجة. فقد العملية أثناء اللعب غير قابل للاستعادة.
3. **P0 BLOCK — انتحال الهوية عند الدمج الساذج:** المحرك يختبر عضوية `ActorID` داخل أعضاء المباراة، لكنه لا يصادق HTTP. يجب أن ينتج منسق الخادم الهوية من bearer/session ويمنع اعتماد الجسم المرسل. هذه مخاطرة دمج، لا استغلال عبر endpoint موجود.
4. **P0 BLOCK — الفن النهائي وTarneeb/Play:** لا GLB بشري أو بيئة مستقلة معتمدة ولا واجهة بطاقات فعلية؛ لا محرك Tarneeb أو عقده؛ لا AAB موقع أو أربعة أجهزة Android تكمل مباراة.
5. **P1 REQUEST_CHANGES — حد الوكيل:** استطلاع أربع هويات من IP واحد يستهلك نظريًا حصة 180/min؛ لا تثق بأي `X-Forwarded-For` غير موثق. العلاج قرار نقل/حافة ومقاييس خدمة بمراجعة عبدالعزيز.
6. **P1 REQUEST_CHANGES — هوية الضيف بعد ضياع إنشاء الجلسة:** `NewGuest` يولد token جديدًا كل استدعاء، ففقد رد الإنشاء قد يترك ضيفًا يتيمًا. يلزم سياسة ترقية/استعادة وهوية طويلة العمر قبل إطلاق الحسابات.
7. **P1 VERIFIED FIX — سجل Android تالف:** قبل الرقعة، `jsonDecode`/cast كان يفشل، وتبقى `initialized=false`، وزر retry يعيد السجل نفسه بلا مخرج. إصلاح D0 أدناه.
8. **P2 معلومة تشغيلية — إيصال غرفة قديم:** قد يعيد replay لعضو باقٍ snapshot قديمًا؛ العميل يقرأ الطاولة بعدها، والإيصال مقصود للتكرار. لا دليل تسرب يد أو دعوة فعالة بهذا وحده.

## 4. الإصلاح الصغير ضمن النطاق المعتمد

**قيمة اللاعب:** استعادة شاشة الدخول عند فساد سجل محلي من دون محو ضيف قابل للحفظ. **الملفات:** `mobile/lib/controller.dart`, `main.dart`, `strings.dart` واختبارات `controller_test.dart`, `widget_test.dart`, `security_regression_test.dart`. لا تغيير خادم أو قواعد أو مشهد.

الآن يصنف المتحكم JSON/بنية الجلسة التالفة، ويبقي السجل كما هو حتى تأكيد اللاعب. إذا كان token قابلًا للقراءة وpending تالفًا، يحتفظ بالرمز ويعرض تنبيهًا بأن الفعل ربما نُفّذ، ثم يحفظ الرمز دون pending ويقرأ `/me` من الخادم. إذا كانت الجلسة نفسها غير قابلة للقراءة، يوضح احتمال فقد هوية الضيف قبل المسح. فشل القراءة المؤقت من Keystore لا يعرض مسحًا، وفشل كتابة الاستعادة لا يغيّر الحالة المنشورة. لا تعاد أي pending إلا بعد التحقق من مسار غرفة متوقع و`action_id` بالشكل الذي ينتجه التطبيق؛ يرفض إعادة POST محفوظ إلى `/v1/guests` مثلًا.

اختبارات الانحدار تستخدم سجلات فاسدة فعليًا، شكل JSON خاطئًا، token سليمًا مع pending تالفة/مسار غير مسموح، إلغاء/تأكيد حوار UI، فشل قراءة المخزن وفشل كتابة الاستعادة. `flutter test` نجح في 19 اختبارًا مع تخطي اختبار live في التشغيل العادي، و`flutter analyze` و`dart format --set-exit-if-changed` و`git diff --check` نجحت. `check_live.sh` المنفصل نجح: خمس فحوص عملية واختبار Flutter بأربع هويات مع خادم Go فعلي، وكلها غرف انتظار؛ `go test -race ./...` و`go vet ./...` نجحا. **الرجوع:** عكس commit الإصلاح على هذا الفرع يعيد سلوك الاستعادة القديم؛ لا مخطط تخزين أو API خادم تغير. لا يمس هذا إصلاح Android مباراة غير موجودة.

## 5. مقترح حفظ مباراة ذري — D2 لمراجعة عبدالعزيز، غير معتمد

نقترح **حدًا منطقيًا للمعاملة** قبل اختيار منتج قاعدة بيانات: `matches` يحمل match ID، نسخة القواعد الثابتة، version، المرحلة، الحالة الخاصة والأيدي ومواد الخلط السرية المشفرة/المحمية؛ `actions` يحمل `(match_id, actor_id, action_id)` فريدًا مع fingerprint ومدخل/version وreceipt؛ `events` تسلسلًا عامًا وخاصًا بكل مقعد؛ `settlements` نتيجة واحدة فريدة؛ و`outbox` رسائل تُرسل بعد الحفظ. يجب ألا تظهر private state أو seed أو أيدي الخصوم في log أو API عام. يتطلب التصميم سياسة احتفاظ ونسخ/استعادة وتشفير وحقوق مشغلين.

مسار الفعل المقترح: (1) تحقق جلسة HTTP وعضوية المقعد خادميًا؛ (2) ابدأ معاملة واقفل المباراة/نسختها؛ (3) إن وجد نفس `action_id` أعد الإيصال المطابق أو ارفض fingerprint مختلفًا؛ (4) تحقق `expected_version` والعقد والدور؛ (5) طبّق المحرك على نسخة منعزلة؛ (6) اكتب حالة المباراة والإيصال والأحداث والتسوية إن انتهت وoutbox **في commit واحد**؛ (7) بعد commit أرسل projection منفصلة لكل مقعد. لا تغادر معلومة يد عبر payload عام. فشل قبل commit لا يغير شيئًا؛ ضياع الرد بعده يحل بإعادة المعرّف؛ سقوط العملية بعد commit وقبل البث يعالجه outbox؛ تنازع فعلين يحسمه version/القفل. الاستعادة تقرأ checkpoint مع سجل مرتب وتتحقق من نسخة القواعد والنتيجة، ولا تعتمد على ذاكرة `Replay()` وحدها.

خيارات التنفيذ — PostgreSQL ونظائره أو مخزن معاملات مناسب — **للمقارنة التقنية فقط**، دون اعتماد مزود أو قاعدة أو بروتوكول. يحتاج عبدالعزيز تقرير isolation/locking، حمل 4 عملاء، سرية النسخ الاحتياطية، migration من snapshot، سياسة الأرشفة والفشل والرجوع. لا نرفع سقف JSON ونعلن توسعًا. لا يلزم Kubernetes افتراضيًا.

## 6. ورقة قرار Trix المطلوبة من البشر

هذه **أسئلة وليست قواعد معتمدة**. لكل إجابة يُطلب اسم صاحب القرار والتاريخ والإصدار وfixture أو مثال نتيجة حدية، ثم مراجعة عبدالعزيز الفنية واعتماد عمار وفق الحوكمة:

| بند العقد | الحالة اليوم / المطلوب حسمه |
|---|---|
| صيغة المباراة | المرشح أربع ممالك × Complex/Trix = ثماني صفقات؛ هل هذا عقد REX النهائي، أم صيغة أخرى؟ |
| المقاعد والموزع/القائد | مالك المملكة الأولى في المرشح حامل 7 الكبة؛ ترتيب المقاعد المرشح 0→1→2→3 وقائد الصفقة مالكها. يجب تحديد الاتجاه ودور الموزع والقائد بكل صفقة. |
| Complex | اتباع اللون وعقوبات -15 للّمة، -10 للديناري، -25 للبنت، -75 لشيخ الكبة في المرشح؛ حسم فتح الكبة، رمي الجزاء، الحالات المشتركة والدبل وقيمه ووقته ومن يأخذه. |
| Trix | بدء كل سلسلة بالولد والامتداد المتلاصق والتمرير عند العجز، نقاط 200/150/100/50 في المرشح؛ حسم أي اختلاف في السماح/الأولوية ونهاية التعادل. |
| إعادة التوزيع/الانقطاع | لا سياسة معتمدة لإعادة توزيع أو مهلة الدور أو خروج اللاعب أو الاستسلام أو الإعادة بعد عودة الشبكة؛ حسمها مع أمثلة قابلة للاختبار. |
| الفصل عن Tarneeb | عقد Tarneeb مستقل للمزايدة والطرنيب والفرق والتسجيل والهدف والتعادل؛ لا تستنتج قواعده من Trix أو اختبارات غرفة تحمل اسم اللعبة. |

تبقى `PublicActivation()` و`/start` مغلقتين حتى تُحفظ نسخة عقد مع مصدر الموافقة وتُكتب اختبارات fixtures القانونية وغير القانونية. لا يتخذ السرب قرار القواعد بدل المؤسسين.

## 7. الطريق الأدنى لأربعة عملاء حقيقيين

بعد بوابة القواعد وقرار المعاملة: أنشئ match من غرفة أربعة أعضاء جاهزين مرة واحدة؛ اشتق كل ActorID من جلسة موثقة؛ اخلط الخادم ويثبت نسخة القواعد؛ يخزن المنسق الحالة الخاصة وإيصالات الأفعال؛ يقدم view لكل مقعد وحده مع version وevent sequence؛ يسمح بالأفعال القانونية حسب الدور؛ يعيد الاتصال بإرسال snapshot مفلتر أو الأحداث المفقودة؛ يمنع ازدواجية action ID والتسوية. يُختبر سيناريو بأربعة عملاء مستقلين يكملون ثماني صفقات ثم Tarneeb بمواصفته، مع فصل الشبكة وkill/restart قبل/بعد commit ونتيجة مساوية بعد الاستعادة. بعد نجاح الاختبار على host تنتقل نفس رحلة المستخدم إلى أربعة أجهزة Android فعلية، ثم قياسات FPS/ذاكرة/حرارة/بطارية وحمل خدمة مختلط طويل. اختبار Flutter بأربعة controllers ومحاكي Android واحد لا يفي بهذه النقطة.

## 8. جاهزية الفن مستقلة

**SW-08: BLOCK.** `production/assets/scene-contract.json` عقد محايد بمواضع المقاعد وست سمات وأربع وجهات، لكنه يحتوي `model=null` و`release_approved=false`. ملفات staging التسعة عشر غير معتمدة، ولا rig/skin/animations في مسحها؛ نموذج الشمال القديم بلا armature أو UV أو حركة. تطبيق Flutter يحمل الشعار وغرفة قوائم فقط، ولا renderer 3D أو بطاقة ديناميكية بالمشهد. المطلوب أصل مستقل بحقوق تجارية ومصدر `.blend` وGLB وUV/PBR وrig وحركات جلوس/ورق، للطاولات والشخصيات والبيئات، مع استيراد وفحص أداء ومقارنة مرجع REX وموافقة الفريق. مرور Khronos Validator شرط بنيوي فقط.

## 9. الحكم الموحّد وحدود الموافقة

**الحكم الهندسي: CHANGES_REQUIRED للمنتج، BLOCK لتفعيل اللعب والإصدار، VERIFIED_IN_SCOPE للإصلاح D0 بعد مراجعات الأمن/Android/QA ونجاح CI على `de72ae5`.** لا تغيير لسجل اعتماد البشر. أبرز اعتراض محفوظ: ممثل الأمن رفض أول إصلاح رغم نجاح الاختبارات لأنه كان يهدر token سليمًا؛ جرى تصحيح المسار ولم تُطمس الملاحظة. لم يثبت أي مراجع اختراقًا قائمًا لأيدي خصوم في API الحالي؛ هذا لأن API المباراة غائب، وليس شهادة سرية بعد بنائه. PR#7 الكبير يحتاج مراجعة قواعد مفصلة؛ ضوابط الضغط الحالية لا تثبت مليون لاعب. القرار العملي التالي هو اعتماد قواعد الإصدار ومراجعة عبدالعزيز لتصميم الحفظ/النقل، ثم بناء رحلة مباراة واحدة حقيقية قبل توسيع الوثائق أو البنية التخمينية.
