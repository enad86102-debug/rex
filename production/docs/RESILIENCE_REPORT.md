## الوظائف والإصلاحات الفعلية

1. حد admission غير منتظر:64 طلب تطبيق متزامنًا افتراضيًا، قابل للتحديد
   داخليًا حتى 256. الزائد يُرفض 503 مع Retry-After قبل قراءة body أو انتظار
   معاملات الحفظ. health متاح أثناء امتلاء هذا الحد. هذا لا يحد اتصالات TCP
   أو TLS أو مقابس نظام التشغيل؛ يلزم حد مستقل عند وكيل TLS في التشغيل.
2. محدد IP يحتفظ بسقف 10,000 سجل ويرفض العناوين الجديدة عند الامتلاء. أصبح
   تنظيف السجلات القديمة مرة في الدقيقة بدل مسحها لكل عنوان جديد عند
   الامتلاء. اختبار يثبت السقف ثم استعادة السعة بعد انتهاء النافذة.
3. نسخ المعاملة أصبح typed copy للخرائط و Audit مع نسخ عميق لمقاعد الطاولات
   وإيصالات الأفعال. أزيل JSON encode/decode إضافي قبل كل معاملة؛ كتابة
   snapshot الذرية و fsync وسلوك إعادة المحاولة لم يتغيرا.
4. اختبار فشل كتابة ready يثبت عدم تغيير المقاعد أوالإيصالات، واختبار
   rollback يمنع تسرب تعديل مقاعد الإيصال إلى الحالة المنشورة.
5. اختبار تسلسلات مولدة:3seeds و 200 حركة لكل seed ، ثمانية حسابات، إنشاء
   وانضمام وجاهزية ومغادرة وإعادة أوامر. يتحقق من atomic rejection ، وتطابق
   replay ، وخصوصية غير الأعضاء، وصحة الحالة، وإعادة فتح الحفظ كل 25 حركة.
6. أداة `server/cmd/rexpressure` تبدأ خادم TLS حقيقيًا بشهادة مختبر موثوقة
   وحفظ مؤقت، ولا تقبل عنوان خدمة عامة. تقيس body كاملًا و status والتأخير
   والتخصيصات، وتتحقق من استمرار أثر ready واحد بعد إعادة فتح الحفظ.
7. مراجع CI المباشرة ل checkout/setup-go/flutter-action مثبتة إلى SHA كاملة،
   من GitHub API ؛ [action-pins.json](../qa/action-pins.json). هذا لا يعني
   مراجعة كودها أو تثبيت كل تبعياتها الداخلية أو كل تنزيلات Android.

البيانات لحساب واحد وطاولة انتظار واحدة، وطلباتقراءة/health وإعادة ready
بنفس action ID. ليست 4096 عملية كتابة مستقلة أو 64 لاعبًا أو مباراة.

كسعة لاعبين أو throughput لكتابة المباريات. الأرقام loopback قصيرة ومحددة
الحمولة، لا SLA إنتاجي أو soak لساعات أو تجربة شبكات هاتف/مناطق متعددة.
